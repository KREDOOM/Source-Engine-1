## Модели (Studio Models)

В движке [[Source Engine 1|Source]] **модели** (или Studio Models) представляют собой комплексные трехмерные ассеты с расширением **`.mdl`**, используемые для рендеринга динамических и статичных объектов (персонажей, оружия, транспорта, элементов окружения).

В отличие от современных движков (Unreal Engine, Unity), куда можно напрямую импортировать готовый файл `.fbx` или `.obj`, конвейер Source 1 устроен по принципу классического программирования: 3D-художник обязан вручную написать текстовый скрипт компиляции **`.qc`** и пропустить промежуточные файлы ассета через консольный компилятор `studiomdl.exe`.

---

## 📂 Анатомия скомпилированной модели (Файловая группа)

После успешной компиляции движок генерирует не один файл, а целую группу связанных бинарных файлов. Если при переносе модели в игру потерять или забыть хотя бы один из них, объект либо вообще не отобразится, либо вызовет мгновенный вылет игры (Crash):

- **`.mdl`** — главный управляющий файл модели. Содержит общую структуру, имена анимаций, костей, бодигрупп, путей к материалам, физические параметры и метаданные. Не содержит саму геометрию.
- **`.vvd` (Valve Vertex Data)** — бинарный файл, содержащий массив всех вершин модели (их координаты, UV-развертку, веса привязки к костям и векторы нормалей вершин).
- **`.dx90.vtx` (Vertex Index Data)** — файл индексов вершин, оптимизированный под аппаратные инструкции DirectX 9. Именно он отвечает за правильный порядок сборки треугольников видеокартой и хранит в себе уровни детализации (**LOD**).
- **`.phy` (Physics Data)** — файл физической модели (коллизии). Содержит упрощенную, грубую геометрию (физбокс), по которой игровой движок рассчитывает столкновения объекта, его массу, плавучесть и хитбоксы.

## 📐 Архитектура файла компиляции (.QC)

Файл **`.qc`** — это текстовый конфигурационный скрипт, написанный на языке KeyValues. Он является «картой сборки», которая указывает компилятору `studiomdl.exe`, какие геометрические файлы взять, как настроить кости, куда привязать физику и в каких папках искать текстуры.

Базовый синтаксис чистого QC-скрипта:

```qc
// 1. Метаданные и пути экспорта
$modelname       "твой_ник/props/wooden_chair.mdl" // Путь внутри папки <game>/models/
$scale           1.0                              // Масштабирование модели при сборке

// 2. Подключение геометрии (Референс-меш)
$body "body"     "wooden_chair_reference.smd"     // Ссылка на исходную геометрию

// 3. Работа с материалами
$cdmaterials     "models/your_name/props/"         // Папка, где движок будет искать файлы .vmt

// 4. Физические свойства поверхности
$surfaceprop     "wood"                           // Звуки ударов, шагов и тип осколков

// 5. Физическая модель коллизии (Физбокс)
$collisionmodel  "wooden_chair_physics.smd"
{
	$mass        15.0                             // Масса объекта в килограммах
	$inertia     1.0                              // Коэффициент инерции
	$damping     0.0                              // Затухание движения
	$rotdamping  0.0                              // Затухание вращения
}

// 6. Базовая статичная анимация (Обязательна для всех моделей)
$sequence "idle" "wooden_chair_reference.smd" fps 1
```

Используйте код с осторожностью.

## 🗂️ Промежуточные форматы данных (Исходники)

Перед тем как попасть в компилятор, 3D-модель экспортируется из графических пакетов (Blender, 3ds Max, Maya) в промежуточные текстовые форматы Valve:

1. **`.smd` (Studio Model Data)** — классический, проверенный временем формат. Бывает двух типов:
    - _Reference (Референс):_ Хранит в себе чистую полигональную сетку объекта, UV-координаты и привязку вершин к скелету (костям).
    - _Animation (Анимация):_ Хранит только данные трансформации костей по кадрам (смещение и поворот). Сетки в ней нет.
2. **`.dmx` (Data Model Exchange)** — более современный и гибкий бинарно-текстовый формат, представленный в поздних ветках движка (Portal 2, CS:GO). Поддерживает сложные Flex-анимации лица персонажей, продвинутый скиннинг и не имеет строгих ограничений старого `.smd`.

Для работы с Blender используется официальный и поддерживаемый комьюнити плагин **Blender Source Tools (BST)**, позволяющий экспортировать оба формата в один клик.

## 🛑 Критические лимиты и технические боли (Troubleshooting)

- **Лимит вершин (Vertex Limit Crash):**  
    В старых ветках Source 1 (и частично в Garry's Mod) существует жесткое аппаратное ограничение компилятора: **не более 65 536 вершин на одну подмодель** (один блок `$body` или `$model`). Если ваша модель слишком высокополигональная (например, 100 000 полигонов), компилятор выдаст ошибку `Too many vertices in studio model`.
    - _Решение:_ Разрезать геометрию в 3D-редакторе на несколько частей и объявлять их в QC через несколько строк `$body` последовательно (например, отдельно кузов машины, отдельно колеса).
- **Катастрофа «Пропавших текстур» (Черно-пурпурная сетка на модели):**  
    Если модель в игре отображается как сплошной шахматный паттерн, это значит, что `.mdl` файл не смог инициализировать материалы.
    - _Причина:_ Движок ищет материал по строгому совпадению: имя текстурного слота, заданное внутри 3D-редактора при экспорте `.smd` (например, `wood_planks`), должно в точности совпадать с именем файла `wood_planks.vmt`. При этом сам `.vmt` должен лежать строго по пути, указанному в строке `$cdmaterials`.
- **Баг «Склеенного физбокса» (Неправильная коллизия):**  
    Если вы создаете стул или раму ворот, игрок не сможет пройти сквозь пустое пространство между ножками или внутри арки. Компилятор по умолчанию натянет на физбокс общую выпуклую оболочку (Convex Hull).
    - _Решение:_ Физбокс нужно собирать из отдельных независимых геометрических коробок (кубов) в 3D-редакторе, а в блоке `$collisionmodel` внутри QC-файла обязательно прописать команду `$concave`. Это заставит компилятор обрабатывать коллизию как вогнутую структуру.

## 🎮 Классификация моделей по назначению на карте

В зависимости от того, как объект должен вести себя в игровом мире (в Hammer Editor и Garry's Mod), модели делятся на три класса. Логика сборки в QC должна соответствовать этим классам:

- **`prop_static`** — абсолютно статичная модель. Не имеет физики, не может двигаться, не обрабатывает кости. Максимально оптимизирована для производительности. Используется для зданий, столбов, заборов, деревьев.
- **`prop_physics`** — физический объект. Обладает массой, может быть сдвинут игроком, реагирует на гравитацию, взрывы и выстрелы. Требует обязательной качественной настройки блока `$collisionmodel` и параметров веса. Используется для бочек, ящиков, оружия, мусора.
- **`prop_dynamic`** — динамическая модель, управляемая скриптами карты или кодом. Может проигрывать сложные скелетные анимации (строка `$sequence`), изменять бодигруппы, открываться, закрываться или следовать за игроком. Используется для дверей, лифтов, персонажей (NPC) и боссов.
